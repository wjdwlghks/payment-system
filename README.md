# Payment System

카드 결제의 **인증 → 승인 → 매입**과 그 이후의 **대사 → 청산 → 정산 → 지급**까지를 다루는
멀티서비스 PG 시뮬레이터입니다.

만든 목적은 다음과 같습니다 —
**외부 호출이 타임아웃되거나 응답이 유실돼도 돈 계산이 어긋나지 않는가.**
그래서 카드사·FDS에 실제로 장애를 주입한 부하 테스트를 돌리고, 끝난 뒤 카드사가 독립적으로
만든 정산 파일과 대사해서 불일치가 0인지를 확인합니다.

```
POST /v1/payment                   인증(+FDS)   카드가 유효한지 확인. 금액을 잡지 않는다
POST /v1/payment/{key}/approve     승인          여기서 사용자에게 "결제 완료"가 보인다
POST /v1/payment/{key}/capture     매입          실제 청구. 원장(회계 기록)은 이때 생긴다
```

## 1. 띄우기

필요한 것은 **Docker**와 [k6](https://k6.io)뿐입니다.

```bash
docker compose up -d --build     # 첫 빌드는 수 분 걸립니다
```

서비스 5개와 MySQL 4개가 뜹니다.

| 서비스 | 포트 | 역할 |
|---|---|---|
| `merchant` | 8081 | 가맹점 — 결제 API를 대신 호출하고 웹훅을 받는다 |
| `payment` | 8082 | **PG(오케스트레이터)** — 이 프로젝트의 본체 |
| `fds` | 8083 | 이상거래 탐지 |
| `card` | 8084 | 카드사 A (`CARD_CORP_A`) |
| `card-b` | 8085 | 카드사 B (`CARD_CORP_B`) |

## 2. 테스트 돌리기

```bash
# 기본값: 확률 0.027 · 150 TPS · 2분 · 인증/FDS/승인에 장애
./scripts/run-consistency-proof.sh

# [확률] [TPS] [기간]
./scripts/run-consistency-proof.sh 0.05 100 2m

# [확률] [TPS] [기간] [장애 단계] — 인증에만 장애
./scripts/run-consistency-proof.sh 0.027 150 2m auth

# 승인과 매입에 장애
./scripts/run-consistency-proof.sh 0.027 150 2m approve,capture
```

이 한 줄이 다음을 순서대로 합니다. 첫 실행은 이미지 빌드까지 10분 안팎, 두 번째부터는
부하 시간 + 1분 남짓입니다(기본값이면 3분 이내).

1. **DB를 전부 비우고** 서비스를 다시 빌드·기동한다 ⚠️ 기존 데이터는 사라집니다
2. 고른 단계에 4종 장애(응답 전/후 유실, 500, connect 실패)를 확률적으로 주입하며 부하를 건다
3. 장애 주입을 끄고, 미확정 건이 전부 확정될 때까지 기다린다
4. 카드사가 자기 데이터로 정산 파일을 생성 → 대사 → 청산 → 정산 → 지급까지 태운다
5. 판정 결과를 **터미널에 표로 출력**한다 (원자료는 `results/*.json`에도 남는다)

### 결과 읽는 법

실행이 끝나면 터미널에 표 두 개가 찍힙니다. 따로 파일을 열어볼 필요는 없습니다.

먼저 **단계별로 몇 건이 어떻게 끝났는지**입니다.

```
=== 단계별 처리 (DB 기준 · 수렴 후) ===
  단계              유입   UNKNOWN       성공  = 즉시 + 복구              실패  = 즉시 + 복구            미확정
  AUTH        18,001     1,871   16,614  = 16,130 + 484      1,387  = 0 + 1,387            0
  FDS         16,614     1,729   15,304  = 14,885 + 419      1,310  = 0 + 1,310            0
  APPROVE     15,304     1,663   14,019  = 13,641 + 378      1,285  = 0 + 1,285            0
  CAPTURE     14,019         0   14,019  = 14,019 + 0            0  = 0 + 0                0
```

`UNKNOWN`은 그 단계에서 응답이 애매해 성공/실패를 단정할 수 없었던 건수입니다. 재시도하지 않고
카드사에 다시 물어서(조회) 확정하며, 그 결과가 `복구` 칸입니다 — 성공으로 확정된 것도, 실패로
확정된 것도 있습니다. **`미확정`은 0이어야 합니다.** 0이 아니면 아직 안 끝난 상태로 대사에
들어간 것이라 뒤의 판정을 믿을 수 없습니다.

위 예시에서 매입(CAPTURE)의 UNKNOWN이 0인 것은 그 단계가 대조군이었기 때문입니다(기본값).

그다음이 **판정**입니다.

```
=== 판정 — 정산파일 5-case 대사 ===
                    CARD_CORP_A  CARD_CORP_B
  카드사에만 있음                    0            0
  PG에만 있음                     0            0
  금액 불일치                      0            0
  상태 불일치                      0            0
  총액 불일치                      0            0
  합계                          0            0

  대사 불일치 0건                    PASS
  장애가 실제로 걸렸는가              PASS 
```

PG가 자기 장부를 자기가 검사하는 게 아니라, **카드사가 자기 데이터로 만든 CSV와 맞춰봅니다.**
합계가 0이면 장애를 맞는 동안에도 이중 청구나 누락 청구가 없었다는 뜻입니다.

**"장애가 실제로 걸렸는가"를 반드시 같이 보세요.** 이 줄이 FAIL이면 정합성이 완벽했던 게 아니라
**장애가 안 걸려서 아무것도 증명하지 못한 런**입니다. (옆 괄호에 조회로 확정된 건수가 같이 찍힙니다.)
